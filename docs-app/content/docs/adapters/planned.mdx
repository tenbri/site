## Use Tenbri from any framework today

An adapter only automates what you can do yourself. Find your tool functions, the ones the agent
calls, and record each call as a decision: `@tenbri.decision` in Python, `decision({...}, fn)` in
TypeScript. Each call then writes:

1. Before the function runs, an **intent**: `principal` is the agent, `action.type` the action,
   `action.target` what it acts on. If the intent cannot be written, the function does not run.
2. After it runs, the **outcome**: `ok`, `refused` when it raises `tenbri.Refused` (throws
   `Refused`), `error` for any other exception (which propagates), `unknown` when cancelled
   (an `AbortError` in TypeScript).

Here is a refund tool, `issue_refund`, recorded that way. `tenbri.init()` opens the stream, as for
the adapters (from `TENBRI_STREAM` and `TENBRI_AGENT` when you pass nothing), and
`tenbri.agent()` (`agent()`) says who acts for a block of code:

<Tabs groupId="lang" persist items={["Python","TypeScript"]}>
<Tab value="Python">

```python title="wrap.py"
import tenbri

tenbri.init("./audit", agent="agent:support")  # or TENBRI_STREAM and TENBRI_AGENT

POLICY = "Refunds up to 500 EUR are automatic."

@tenbri.decision(
    "issue_refund",
    target="stripe:{charge}",              # a template of the arguments
    policy="policy:refund@14",             # the rule that allowed it
    inputs=[("policy:refund", "14", POLICY)],  # what it relied on, by keyed digest
)
def issue_refund(charge: str, amount: int) -> str:
    if amount > 500:
        raise tenbri.Refused("over the refund ceiling")  # recorded as refused
    return f"refunded {amount} EUR of {charge}"  # your tool

print(issue_refund("ch_123", 30))
with tenbri.agent("agent:billing"):  # who acts, for this block
    try:
        issue_refund("ch_456", 900)
    except tenbri.Refused as e:
        print("refused:", e)

log = tenbri.default()
for m in log.query(action="issue_refund"):
    e = m.entry
    print(e["seq"], e["phase"], e.get("status", ""), e["principal"]["id"], e["action"]["target"])
print("verified:", log.verify(log.fingerprint).ok)
```

```sh
python wrap.py
```

```text
refunded 30 EUR of ch_123
refused: over the refund ceiling
3 intent  support stripe:ch_123
4 outcome ok support stripe:ch_123
5 intent  billing stripe:ch_456
6 outcome refused billing stripe:ch_456
verified: True
```

The decorator works the same on `async def` functions. `target` and `subject` are templates of the
function's arguments (`"stripe:{charge}"`, `"{order.id}"`) or functions of them; `inputs` can be a
function of the arguments too. Who acts is `principal=`, else the innermost
`with tenbri.agent(...)`, else `init(agent=...)` or `TENBRI_AGENT`: with none, the call raises
`InvalidRequestError: no principal`.

</Tab>
<Tab value="TypeScript">

```ts title="wrap.ts"
import { Refused, agent, decision, init } from 'tenbri'

const log = await init({ stream: './audit', agent: 'agent:support' }) // or TENBRI_STREAM and TENBRI_AGENT

const POLICY = 'Refunds up to 500 EUR are automatic.'

const issueRefund = decision(
  {
    action: 'issue_refund',
    target: 'stripe:{charge}', // a template of the first argument
    policy: 'policy:refund@14', // the rule that allowed it
    inputs: [{ ref: 'policy:refund', version: '14', content: POLICY }], // what it relied on, by keyed digest
  },
  async ({ charge, amount }: { charge: string; amount: number }) => {
    if (amount > 500) throw new Refused('over the refund ceiling') // recorded as refused
    return `refunded ${amount} EUR of ${charge}` // your tool
  },
)

console.log(await issueRefund({ charge: 'ch_123', amount: 30 }))
// who acts, for what the callback runs
await agent('agent:billing', () => issueRefund({ charge: 'ch_456', amount: 900 })).catch((e) => console.log('refused:', e.message))

for (const { entry: e } of await log.query({ action: 'issue_refund' })) {
  console.log(e.seq, e.phase, e.status ?? '', e.principal?.id, e.action?.target)
}
console.log('verified:', (await log.verify(log.fingerprint!)).ok)
```

```sh
node wrap.ts
```

```text
refunded 30 EUR of ch_123
refused: over the refund ceiling
3 intent  support stripe:ch_123
4 outcome ok support stripe:ch_123
5 intent  billing stripe:ch_456
6 outcome refused billing stripe:ch_456
verified: true
```

`decision()` returns an async function. `target` and `subject` are templates of the arguments
(`'stripe:{charge}'` reads the first argument's `charge`, `'{1}'` is the second argument) or
functions of them. Who acts is `principal`, else the innermost `agent(...)` scope, else
`init({ agent })` or `TENBRI_AGENT`.

</Tabs>

The first intent, as stored (signatures and hashes shortened). The policy's text is pinned by its
keyed digest, keyed by the stream's local key store, so no secret goes in your code:

If a person approved the call, write an `approval` entry first and name it from the decision, as
the adapters do. For full control (several streams, your own drafts), the stream itself has
`intent`, `outcome` and `append`: see the bindings' READMEs.

### From a shell or another language

Without a binding, write the same intent and outcome with the CLI, or through `tenbrid` over REST:

<Tabs groupId="lang" persist items={["CLI","REST"]}>
<Tab value="CLI">

For shell-driven agents and scripts. `tenbri append` reads a draft entry on stdin and prints it as
stored; the script uses `jq` to read the intent's id. A draft for the CLI carries every required
field, `source` included.

```sh title="refund.sh"
#!/bin/sh
# The tool call, wrapped by hand: intent before, outcome after.
set -e
export TENBRI_KEYS=./keys
[ -d ./audit ] || tenbri init ./audit

intent=$(tenbri append ./audit <<JSON
{"kind":"decision","phase":"intent","source":"sdk","principal":{"kind":"agent","id":"support"},
 "action":{"type":"issue_refund","target":"stripe:ch_123"}}
JSON
)
id=$(printf '%s' "$intent" | jq -r .id)

# Run the tool only once its intent is durable.
if ./issue-refund ch_123; then status=ok; else status=error; fi

tenbri append ./audit <<JSON
{"kind":"decision","phase":"outcome","source":"sdk","intent":"$id","status":"$status",
 "principal":{"kind":"agent","id":"support"},"action":{"type":"issue_refund","target":"stripe:ch_123"}}
JSON
```

```sh
./refund.sh
```

`./issue-refund` stands for your tool. A draft the writer refuses prints
`tenbri: entry rejected: <code>: <detail>` and exits 2, so `set -e` stops before the tool runs: a
draft without `source`, for example, is rejected with `invalid_field`.

</Tab>
<Tab value="REST">

From any language, through `tenbrid`. Start it with a stream and a token as in
[tenbrid over REST](/docs/examples/tenbrid-rest/); the token's principal goes on every entry, and
the server checks action schemas. `curl -f` exits non-zero when the intent is refused, so `set -e`
stops before the tool runs.

```sh title="refund-rest.sh"
#!/bin/sh
set -e
API=http://127.0.0.1:7070/v1/streams/support
# The intent: its Idempotency-Key is the entry id, a ULID your client makes, so a retry is safe.
intent=$(curl -sf -X POST "$API/intents" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: 01K7ZJ4Q3V8M2R6T9W1X5Y7Z0B" \
  -H "Content-Type: application/json" \
  -d '{"action":{"type":"issue_refund","target":"stripe:ch_123"}}')
id=$(printf '%s' "$intent" | jq -r .entry.id)

# Run the tool only once its intent is durable.
if ./issue-refund ch_123; then status=ok; else status=error; fi

curl -sf -X POST "$API/outcomes" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: 01K7ZJ4R8N2B6C4D9E1F3G5H7K" \
  -H "Content-Type: application/json" \
  -d "{\"intent\":\"$id\",\"status\":\"$status\"}"
```

```sh
./refund-rest.sh
```

```text

{"entry":{"action":{"target":"stripe:ch_123","type":"issue_refund"},"id":"01K7ZJ4R8N2B6C4D9E1F3G5H7K","intent":"01K7ZJ4Q3V8M2R6T9W1X5Y7Z0B","kind":"decision","phase":"outcome","prev":"sha256:39b7833c…","principal":{"id":"support","kind":"agent"},"seq":4,"sig":"ed25519:51d619c6…","signer":"sess:2026-10-20:dbd0e69efa58","source":"sdk","status":"ok","stream":"tnb1:1786a17fc8a9690c394e4c8c00eabfaa","ts":"2026-10-20T14:52:21.574Z","v":1},"replayed":false}
```

Generate a fresh ULID per entry in your client: the fixed keys here are for the example. Sending
the same key again returns the original entry with `"replayed":true`.

</Tab>
</Tabs>

Then read the stream back with `tenbri tail`, `tenbri show` and `tenbri verify`, or the bindings'
`query` and `verify`, as on any adapter page. On the machine that ran `tenbri init`, `verify` uses
the pin it recorded and needs no `--key`; anywhere else, and for a stream `init()` created, pass
`--key`. See [Streams and entries](/docs/concepts/streams-and-entries/)
for the fields and the [entry format](/docs/reference/entry-format/) for the exact draft shape.
