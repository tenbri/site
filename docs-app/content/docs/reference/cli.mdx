---
title: tenbri CLI
description: Every tenbri subcommand and flag, what each prints, its exit codes and the environment it reads.
---


`tenbri` creates streams, appends entries, verifies, queries, shows and follows them, seals checkpoints,
makes and checks receipts, manages data keys and erasure, and checks streams against action
schemas. It ships with the `keychain` and `s3` Cargo features on by default.

```text
tenbri [--keys DIR] <COMMAND>
```

All output described below goes to stdout. Errors go to stderr as `tenbri: <message>`.

## Global options

| Flag | Value | Default | Meaning |
| --- | --- | --- | --- |
| `--keys` | `DIR` | `$TENBRI_KEYS`, else `$XDG_CONFIG_HOME/tenbri/keys`, else `~/.config/tenbri/keys` (`%APPDATA%\tenbri\keys` on Windows) | Keys directory. Never inside a stream. |
| `--help` | | | Print help. |
| `--version` | | | Print the version. |

Commands that need keys (`init`, `append`, `checkpoint`, `erase`, `keys`) fail with exit code 2 and
`no keys directory: pass --keys or set TENBRI_KEYS` when no directory can be found.

A stream `PATH` is a local directory (`<root>/<stream>`) or an object-store URL
(`s3://bucket/<root>/<stream>`, `r2://bucket/<root>/<stream>`). See
[Storage](/docs/reference/storage/).

Every command that takes a stream `PATH` (`init`, `append`, `verify`, `query`, `show`, `tail`,
`checkpoint`, `receipt create`, `erase`, `keys list`, `keys export`, `keys rotate` and
`index rebuild`) reads it from `TENBRI_STREAM` when it is left out:

```sh
export TENBRI_STREAM=audit/support
tenbri verify
tenbri tail -n 6 --no-follow
tenbri show 4
```

With neither, the command exits 2 with clap's `the following required arguments were not
provided: <PATH>`; `show` exits 2 with `no stream: pass one, or set TENBRI_STREAM`.

A `--key` value is a fingerprint `sha256:<64 hex>` or a public key `ed25519:<64 hex>`; a public key
is turned into its fingerprint. Anything else fails with
`--key <value>: expected sha256:<64 hex> or ed25519:<64 hex>` (exit 2). Without `--key`, `verify`,
`show` and the one-line output of `query` and `tail` use the fingerprint `tenbri init` recorded
for the stream on this machine, if there is one ([Pins](#pins)).

## init

Create a stream and its stream key; print the fingerprint to pin.

```text
tenbri init <PATH> [--keychain]
```

| Argument or flag | Meaning |
| --- | --- |
| `PATH` | A directory that does not exist or is empty, or an empty object-store prefix |
| `--keychain` | Keep the secret keys in the OS keychain (macOS Keychain, Windows Credential Manager) instead of key files. Only with the `keychain` feature. |

`init` writes the genesis entry (the stream key certifying itself) and a session key certification,
so a new stream holds 2 entries. It then appends the stream's location and fingerprint to
`<keys>/pins` ([Pins](#pins)), so `verify` on this machine needs no `--key`. It fails (exit 2)
with `<PATH> is not empty` for a used directory,
`<PATH> already holds a stream` when a `HEAD` exists, and when the keys directory and the stream
directory contain each other.

Output:

```text
created stream <stream id> at <PATH>
stream key fingerprint (pin it): <sha256:...>
keys: <key directory>
pinned in <keys>/pins: tenbri verify <PATH> uses it
verify with: tenbri verify <PATH> --key <sha256:...>
```

The `verify with` line is the command for anyone without this machine's pins file: an auditor, CI,
another laptop.

## append

Append one entry, read as JSON on stdin; print it as stored.

```text
tenbri append <PATH> < entry.json
```

- The input is a draft: canonicalised, with duplicate keys and non-integers rejected, never
  repaired. It must not contain the members the writer fills (`v`, `stream`, `seq`, `prev`,
  `signer`, `sig`); `id` and `ts` may be given. See [Entry format](/docs/reference/entry-format/).
- Before appending, the writer writes a `reconcile` entry (`status: unknown`) for every intent open
  longer than 1 hour, except the intent this draft closes.
- `tenbri append` does not check action schemas; `tenbrid` and `tenbri schema check` do.
- A draft that does not parse prints `tenbri: stdin: <code>: <detail>`; one the writer refuses
  prints `tenbri: entry rejected: <code>: <detail>`. Both exit 2; nothing is written.
- An `invalid_field` error is followed by the allowed values of every enumerated field and a
  pointer to the example in `tenbri append --help`. The detail no longer carries serde's line and
  column, which pointed into the canonicalised bytes rather than what you typed:

  ```text
  $ echo '{"kind":"decision","phase":"intent","source":"bot","principal":{"kind":"agent","id":"a"},"action":{"type":"x"}}' | tenbri append audit/support
  tenbri: stdin: invalid_field: unknown variant `bot`, expected one of `sdk`, `proxy`, `ingest`
  allowed values:
    kind            decision, approval, key, reconcile, note
    phase           intent, outcome (decision entries only)
    source          sdk, proxy, ingest
    status          ok, error, refused, unknown (outcomes and reconciles)
    principal.kind  agent, person, service
    durability      local, replicated, postgres
    links[].rel     cause, handoff, approval
  an example: tenbri append --help
  ```

`tenbri append --help` ends with a working decision intent, its outcome and the same list of
allowed values:

```text
The writer fills v, stream, seq, prev, signer and sig; id and ts are optional. A decision intent
needs kind, phase, source, principal and action:

  echo '{"kind":"decision","phase":"intent","source":"sdk",
         "principal":{"kind":"agent","id":"support-bot"},
         "action":{"type":"reply_ticket","target":"zendesk:ticket/1042"}}' | tenbri append ./audit/support

Its outcome names the intent's id and adds a status:

  {"kind":"decision","phase":"outcome","source":"sdk","intent":"<id>","status":"ok",
   "principal":{"kind":"agent","id":"support-bot"},"action":{"type":"reply_ticket"}}

Every field and rule: spec/format-v1.md, section 4.

allowed values:
  kind            decision, approval, key, reconcile, note
  ...
```

Output: the stored entry, canonical JSON on one line.

```json
{"action":{"target":"t:1","type":"reply_ticket"},"id":"...","kind":"decision",...,"v":1}
```

## verify

Check canonical bytes, chain, signatures and keys against a pinned key.

```text
tenbri verify <PATH> [--key FINGERPRINT] [--checkpoint FILE]
```

| Flag | Meaning |
| --- | --- |
| `--key FINGERPRINT` | Fingerprint (`sha256:...`) or public key (`ed25519:...`) of the stream's genesis key. Default: the pin `tenbri init` recorded for this stream in `<keys>/pins` ([Pins](#pins)). |
| `--checkpoint FILE` | A checkpoint (C2SP signed note) seen before. The stream must still hold exactly the entries it covers, so truncation and rewrites behind it are caught. |

When the stream has checkpoints of its own, `verify` also checks it against its latest one.

Output, in the order printed:

| Case | Lines | Exit |
| --- | --- | --- |
| Stream broken | `broken at seq <n>: <code>: <detail>`, then `<k> entries verified before it, stream <id>`, with ` (the pin recorded in <keys>/pins)` when the pin came from there | 1 |
| `--checkpoint` matches | `matches checkpoint <origin> at size <size>` | continues |
| `--checkpoint` does not match | `broken at seq <n>: <code>: <detail>`, then `against checkpoint <origin> at size <size>; the stream has <k> entries` | 1 |
| Stream has its own checkpoint | `matches its latest checkpoint, at size <size>` | continues |
| Pinned with `--key` | `verified <k> entries, stream <id>, pinned to <fingerprint>` | 0 |
| Pinned by the recorded pin | `verified <k> entries, stream <id>, pinned to <fingerprint> (the pin recorded in <keys>/pins)` | 0 |
| No `--key` and no recorded pin | `consistent: <k> entries, stream <id>`, then `NOT pinned: this only shows the stream agrees with its own genesis key; pass --key <fingerprint>`, then the genesis key and the exact command to pin it | 3 |

On the machine that created the stream with `tenbri init`, `verify` needs no `--key`:

```text
$ tenbri verify audit/support
verified 4 entries, stream tnb1:cb2db297f1a4250ac01da3d5eaa8498f, pinned to sha256:cb2db297f1a4250ac01da3d5eaa8498fa331d9f5217f792468587b8f0972d104 (the pin recorded in /…/tenbri-demo/keys/pins)
```

Anywhere else (another machine, another keys directory, or a stream created by `init()` in Python
or TypeScript, which records no pin), `verify` never pins for you. It exits 3 and prints the
command to run once you have checked the fingerprint with the stream's owner:

```text
$ tenbri verify audit/support
consistent: 4 entries, stream tnb1:cb2db297f1a4250ac01da3d5eaa8498f
NOT pinned: this only shows the stream agrees with its own genesis key; pass --key <fingerprint>
its genesis key is sha256:cb2db297f1a4250ac01da3d5eaa8498fa331d9f5217f792468587b8f0972d104; if the stream's owner gave you that fingerprint, pin it:
  tenbri verify audit/support --key sha256:cb2db297f1a4250ac01da3d5eaa8498fa331d9f5217f792468587b8f0972d104
```

The fingerprint in that message is read from the stream itself, so it proves nothing until you
compare it with the one you were given. `--key` always wins over the recorded pin.

A malformed `--checkpoint` file exits 2. A checkpoint does not replace the pin: without `--key` or
a recorded pin the exit code is still 3. Codes are listed in [Errors](/docs/reference/errors/).

## query

Print the entries matching every filter given, in sequence order: one line per entry on a
terminal; one JSON per line, each with its verification status, seq, entry hash and what the answer
is current to, when stdout is a pipe or a file.

```text
tenbri query <PATH> [--input REF@VERSION]... [--action TYPE] [--principal KIND:ID] [--target TARGET]
                    [--subject HANDLE] [--rule REF@VERSION] [--since TIME] [--until TIME]
                    [--trace TRACE_ID] [--status STATUS] [--after SEQ] [--limit N] [--verify]
                    [--key FINGERPRINT] [--json | --pretty] [--all]
```

| Flag | Meaning |
| --- | --- |
| `--input REF@VERSION` | An input the entry used, as `ref@version` (`policy:refund@14`), or `ref` for any version. Repeat to require several. |
| `--action TYPE` | The action type (`reply_ticket`) |
| `--principal KIND:ID` | The principal (`agent:support-assistant`) |
| `--target TARGET` | The action target, exactly |
| `--subject HANDLE` | The subject handle |
| `--rule REF@VERSION` | The rule, as `ref@version`, or `ref` for any version |
| `--since TIME` | Entries at or after this time: `2026-10-20T09:00:00.000Z`, `2026-10-20T09:00:00Z`, `2026-10-20` (midnight UTC), or a duration ago (`90s`, `15m`, `1h`, `7d`). Compared with `ts`, the writer's claimed time. |
| `--until TIME` | Entries before this time, in the same forms |
| `--trace TRACE_ID` | The OpenTelemetry trace id |
| `--status STATUS` | An outcome's status: `ok`, `error`, `refused` or `unknown` |
| `--after SEQ` | Only entries after this sequence number, the cursor of the previous page. Default `0`. |
| `--limit N` | At most this many entries. When more match, `tenbri: more entries match; next page: --after <seq>` goes to stderr. |
| `--verify` | Also read and verify the whole stream, signatures included, and check the index's answers against it |
| `--key FINGERPRINT` | Pin the stream's genesis key. On one-line output, the default is the pin `tenbri init` recorded ([Pins](#pins)); JSON output uses `--key` only. |
| `--json` | One JSON object per line, as when stdout is not a terminal. Not with `--pretty`. |
| `--pretty` | One line per entry, as when stdout is a terminal |
| `--all` | On one-line output, print key entries too; they are hidden by default. JSON output always has them. |

Every filter given must match.

### Output on a terminal

One line per matching entry: seq, `ts`, kind and phase, principal, action type and target, status
(`-` for none) and the verification status:

```text
$ tenbri query audit/support --action refund
     3  2026-10-20T16:50:14.926Z  decision intent   agent:support-assistant  refund order:8812                -        verified
     4  2026-10-20T16:50:14.955Z  decision outcome  agent:support-assistant  refund order:8812                ok       verified
```

Here no `--key` was given and the stream was created on this machine, so the recorded pin applies
and the rows are `verified`. Without a pin they are `unpinned`; from an index, `indexed` (see the
table below). Key entries (`kind` `key`) are left out unless `--all`.

### Output to a pipe, or with `--json`

The same bytes as before one-line output existed, one JSON object per matching entry:

```json
{"verification":"indexed","entry":{...},"seq":4,"hash":"sha256:bcf0853b…","as_of":{"stream":"tnb1:dc736478ac6b04bad25e3a3a6f8d71aa","seq":4,"hash":"sha256:bcf0853b…","checkpoint":4}}
```

`seq` and `hash` are the entry's sequence number and entry hash. `as_of` is what the answer is
current to: the stream, the last sequence number read, its entry hash and, from an index, the size
of the latest checkpoint at or below it. JSON output does not use the recorded pin, so scripts get
the same `verification` as before: `unpinned` without `--key`. Pass `--key` in scripts:

```sh
tenbri query audit/support --action refund --key "$PIN" | jq -c '{seq, verification, phase: .entry.phase, status: .entry.status}'
```

```text
{"seq":3,"verification":"verified","phase":"intent","status":null}
{"seq":4,"verification":"verified","phase":"outcome","status":"ok"}
```

Where the answer comes from decides `verification`:

| Case | How `query` reads | `verification` |
| --- | --- | --- |
| No index | Reads and verifies the whole stream | `verified` with `--key` (or, on one-line output, the recorded pin), `unpinned` without |
| An index (see [index rebuild](#index-rebuild)) | Brings the index up to HEAD, finds the answers in it, then re-reads the batches holding them and checks each entry's hash and bytes against them | `indexed` |
| An index and `--verify` | Also reads and verifies the whole stream and checks each answer's entry hash against it | `verified` with `--key` (or, on one-line output, the recorded pin), `unpinned` without |

An answer from the index is never the index's own copy of an entry: every query re-reads, from
storage, the batches that hold the entries it returns, and compares each entry's hash and stored
line with the index's. Only those batches are read. `indexed` means exactly that: the answers are
the bytes in storage now, but signatures, the chain and the rest of the stream are not checked;
that is `--verify`'s job.

If a batch holding an answer was edited on disk after it was indexed, `query` prints nothing to
stdout and exits 1:

```text
$ tenbri query audit/support --target zendesk:ticket/9
tenbri: the stream changed under the index at seq 3: run `tenbri verify`
```

A query whose answers all come from other batches still answers from the index. With `--verify`,
the same edit is caught as a broken stream instead:

```text
$ tenbri query audit/support --target zendesk:ticket/9 --verify --key sha256:34f35761…
tenbri: the stream does not verify: broken at seq 3: bad_signature: the signature does not verify
```

If the stream does not verify, `query` prints `tenbri: the stream does not verify: broken at seq
<n>: ...` and exits 1. With `--verify`, an index that disagrees with the stream exits 1 with
``the index disagrees with the stream at seq <n>: run `tenbri index rebuild` ``. A time that does
not parse exits 2 with `--since <value>: expected a time (2026-10-20T09:00:00Z, 2026-10-20) or a
duration (1h)`.

## index rebuild

Delete the stream's index and build it again from every batch.

```text
tenbri index rebuild <PATH> [--backend sqlite|parquet]
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--backend` | `sqlite` | `sqlite` (one file, `index.sqlite`) or `parquet` (a `parquet/` directory any Arrow tool reads) |

The index is a derived view that `query` uses; deleting it loses nothing. It lives in
`$TENBRI_INDEX_DIR`, else the user's cache directory (`~/Library/Caches/tenbri/index` on macOS,
`$XDG_CACHE_HOME/tenbri/index` or `~/.cache/tenbri/index` elsewhere, `%LOCALAPPDATA%\tenbri\index`
on Windows), one directory per stream named after its id with `:` as `-`. Once it exists, every
`query` brings it up to HEAD first, and checks its answers against the batches in storage
([query](#query)). Entries of a subject whose keys were erased are left out, and
`tenbri erase` deletes that subject's rows from an existing index.

Output:

```text
indexed 4 entries of tnb1:dc736478ac6b04bad25e3a3a6f8d71aa (sqlite) at <index dir>/tnb1-dc736478ac6b04bad25e3a3a6f8d71aa
latest checkpoint: size 4
```

The second line appears when the stream has a checkpoint.

## tail

Print the last entries, then follow new ones as they are written.

```text
tenbri tail <PATH> [-n LINES] [--no-follow] [--key FINGERPRINT] [--json | --pretty] [--all]
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `-n LINES` | `10` | How many existing entries to print first |
| `--no-follow` | off | Print and exit instead of following |
| `--key FINGERPRINT` | on one-line output, the recorded pin | Pin the stream's genesis key ([Pins](#pins)). JSON output uses `--key` only. |
| `--json` | off | Each entry as canonical JSON, as when stdout is not a terminal. Not with `--pretty`. |
| `--pretty` | off | One line per entry, as when stdout is a terminal |
| `--all` | off | On one-line output, print key entries too |

On a terminal, one line per entry, in the same columns as [query](#output-on-a-terminal); the last
column is `verified` when the stream is pinned (`--key` or the recorded pin) and `unpinned`
otherwise. Key entries are hidden unless `--all`, and `-n` counts the entries printed:

```text
$ tenbri tail audit/support -n 2 --no-follow
     3  2026-10-20T16:50:14.926Z  decision intent   agent:support-assistant  refund order:8812                -        verified
     4  2026-10-20T16:50:14.955Z  decision outcome  agent:support-assistant  refund order:8812                ok       verified
$ tenbri tail audit/support --no-follow --all
     1  2026-10-20T16:50:14.879Z  key               -                        -                                -        verified
     2  2026-10-20T16:50:14.895Z  key               -                        -                                -        verified
     3  2026-10-20T16:50:14.926Z  decision intent   agent:support-assistant  refund order:8812                -        verified
     4  2026-10-20T16:50:14.955Z  decision outcome  agent:support-assistant  refund order:8812                ok       verified
```

To a pipe or with `--json`: each entry as canonical JSON on one line, key entries included, as
before. While following, `tail` polls the stream every 500 ms. A stream that stops verifying exits
1.

## show

Print one entry, by sequence number or id, with the intent, approval, outcome or reconcile it is
linked to, and whether the stream verifies.

```text
tenbri show [PATH] <SEQ|ID> [--key FINGERPRINT] [--json | --pretty]
```

| Argument or flag | Meaning |
| --- | --- |
| `PATH` | The stream. Leave it out to use `TENBRI_STREAM`: `tenbri show 4`. |
| `SEQ` or `ID` | The entry's sequence number or id |
| `--key FINGERPRINT` | Pin the stream's genesis key. Default: the pin `tenbri init` recorded ([Pins](#pins)). |
| `--json` | One JSON object per entry of the chain, as when stdout is not a terminal. Not with `--pretty`. |
| `--pretty` | Fields and chain, as when stdout is a terminal |

`show` reads and verifies the whole stream first. The chain is the entry, the intent it belongs to
(itself, or the one its outcome or reconcile names), every outcome or reconcile of that intent,
the approvals they cite, and any entry that cites this entry as its approval.

On a terminal, the entry's header line (seq, kind and phase, id), `ts`, its entry hash, its other
fields in key order (`principal` and `action` shortened as in `query`; objects as canonical
JSON), the verification, then the chain in `query`'s columns with `>` on the entry shown:

```text
$ tenbri show audit/support 4
seq 4  decision outcome  01M5D3H09B0GJM6DT77MKV7FAQ
  ts           2026-10-20T16:50:14.955Z
  hash         sha256:7281ba194d6e0d0e097d0af6fc8b5f38dc2f168310d715a2e3b6b8eb5b16c3cb
  action       refund order:8812
  intent       01M5D3H08E42WJXBVR8BB5MTXD
  principal    agent:support-assistant
  signer       sess:2026-10-20:66567044e13c
  source       sdk
  status       ok
  verification verified, pinned to sha256:cb2db297f1a4250ac01da3d5eaa8498fa331d9f5217f792468587b8f0972d104 (recorded in /…/tenbri-demo/keys/pins)

chain:
      3  2026-10-20T16:50:14.926Z  decision intent   agent:support-assistant  refund order:8812                -        verified
>     4  2026-10-20T16:50:14.955Z  decision outcome  agent:support-assistant  refund order:8812                ok       verified
```

The `chain:` block is left out when the entry is linked to nothing else (a key entry, a note).
The `verification` line reads `verified, pinned to <fingerprint>` with `--key`, adds
`(recorded in <keys>/pins)` with the recorded pin, and without either:

```text
  verification unpinned: consistent with its own genesis key only; `tenbri verify audit/support` prints the --key to pin
```

Off a terminal or with `--json`, one JSON object per entry of the chain, in sequence order:
`{"verification":"verified","entry":{...},"seq":3,"hash":"sha256:..."}`, with `verification`
`verified` or `unpinned`.

| Case | Message | Exit |
| --- | --- | --- |
| Found | the entry and its chain | 0 |
| No such entry | `tenbri: no entry <SEQ or ID> in <PATH>` | 2 |
| No `PATH` and no `TENBRI_STREAM` | `tenbri: no stream: pass one, or set TENBRI_STREAM` | 2 |
| The stream does not verify | `tenbri: the stream does not verify: broken at seq <n>: <code>: <detail>` | 1 |

## checkpoint

Seal and sign a checkpoint of the whole stream now; with `--tsa`, timestamp it (RFC 3161).

```text
tenbri checkpoint <PATH> [--tsa URL]
```

| Flag | Meaning |
| --- | --- |
| `--tsa URL` | URL of an RFC 3161 timestamp authority. Its token is stored next to the checkpoint (`anchors/<size>.tsr`) and goes into receipts. |

Output:

```text
checkpoint at size <n>: checkpoints/<n, 12 digits>.note
timestamped by <URL>: anchors/<n, 12 digits>.tsr
```

The second line appears with `--tsa`; if the checkpoint already has a token, it reads
`already timestamped: anchors/<n, 12 digits>.tsr` instead.

## receipt create

Write a receipt for entries of a stream: the entries, the stream's key history, a signed checkpoint
covering them with their inclusion proofs, and its RFC 3161 token if it has one.

```text
tenbri receipt create <PATH> --entry SEQ|ID [--entry ...] [--out FILE] [--key FINGERPRINT]
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--entry <SEQ or ID>` | required | An entry's sequence number or id; repeat for a receipt proving several |
| `--out FILE` | stdout | Where to write the receipt |
| `--key FINGERPRINT` | | Check the stream against this fingerprint while reading it |

Exits 1 with `the stream does not verify: ...` when the stream is broken.

## receipt verify

Check a receipt offline against a pinned stream key: no network, no access to the stream.

```text
tenbri receipt verify <FILE> --key FINGERPRINT [--tsa-roots PEM]
```

| Flag | Meaning |
| --- | --- |
| `--key FINGERPRINT` | Required. Fingerprint or public key of the stream's genesis key. |
| `--tsa-roots PEM` | Root certificates of the timestamp authorities you trust. Without it, RFC 3161 tokens in the receipt are not checked. |

Output when it verifies (exit 0):

```text
proves seq <n> (<kind> [<phase>]), id <id>, ts <ts> (claimed by the writer)
in stream <origin>, checkpoint at size <size>, pinned to <fingerprint>; key history: <k> key entries
timestamped by <tsa> at <time> (RFC 3161): the checkpoint existed then
```

One `proves` line per entry; one `timestamped` line per token with `--tsa-roots`. Without
`--tsa-roots`, a receipt with tokens prints
`<k> RFC 3161 token(s) NOT checked: pass --tsa-roots <pem> to trust a timestamp authority`. A
receipt that fails prints `receipt does not verify: <reason>` and exits 1.

## schema check

Validate `tenbri.toml`, then every entry of the given streams against it.

```text
tenbri schema check [PATHS]... [--schema FILE]
```

| Argument or flag | Default | Meaning |
| --- | --- | --- |
| `PATHS` | none | Streams to check: directories or `s3://` / `r2://` URLs |
| `--schema FILE` | `tenbri.toml` | The schema file |

Output and exit codes are in [Action schemas](/docs/reference/schemas/#tenbri-schema-check).

## erase

Delete a subject's data keys, so its bodies and input digests can no longer be read or confirmed,
and record the erasure in the stream. The chain, checkpoints and receipts still verify.

```text
tenbri erase <PATH> (--subject HANDLE | --tenant) --reason REASON [--by ID] [--yes]
```

| Flag | Meaning |
| --- | --- |
| `--subject HANDLE` | The subject whose data keys to delete |
| `--tenant` | The tenant's keys, used by entries without a subject |
| `--reason REASON` | Required. A reference such as the request id (`dsr:2026-1042`), recorded in the erasure note. |
| `--by ID` | Who asked for it, recorded as the note's principal (a person id) |
| `--yes` | Do not ask for confirmation |

Exactly one of `--subject` and `--tenant`. Without `--yes`, `erase` asks you to type the handle (or
`tenant`); anything else exits 2 with `not confirmed; nothing was erased`.

The stream must verify and this machine must hold a key to sign with before anything is deleted.
With `--subject`, the subject's rows are also deleted from the stream's query index, if it has
one.

Output: `erased <subject HANDLE | tenant>: <n> data key epochs deleted; erasure recorded at seq <seq>`.

```text
erased subject subj_7f3c91d2: 2 data key epochs deleted; erasure recorded at seq 7
```

## keys list

List the signing keys and the data keys (subjects and key epochs); never a secret.

```text
tenbri keys list <PATH>
```

Output:

```text
signing keys of <stream id> (<key directory>):
  <key id> <stream|session> <ed25519:...>[ until <not_after>]
data keys (<data key directory>):
  <subject HANDLE | tenant>: epochs <first>..<last>, newest made <created>
```

## keys export

Print a subject's data keys as JSON, for a backup kept apart from the log.

```text
tenbri keys export <PATH> (--subject HANDLE | --tenant) [--digest]
```

| Flag | Meaning |
| --- | --- |
| `--digest` | Only the digest keys: enough to confirm input digests, never to open a body |

Output: `{"epochs": [{"created", "epoch", "key"}...], "stream", "subject"}`, pretty-printed; with
`--digest`, each epoch has `digest_key` instead of `key`. With no key held (erased, or never made
here), it exits 2 with `no data key for subject "<HANDLE>": erased, or never held here`.

## keys rotate

Start a new data key epoch for a subject and record it in the stream. Older epochs keep opening
older data until erased.

```text
tenbri keys rotate <PATH> (--subject HANDLE | --tenant) [--by ID]
```

| Flag | Meaning |
| --- | --- |
| `--by ID` | Who rotated, recorded as the note's principal (a person id) |

Output: `<subject HANDLE | tenant>: new data key epoch <n>, recorded at seq <seq>`. These are data
keys; the CLI does not rotate signing keys ([Keys](/docs/concepts/keys/#rotation)).

## Pins

`tenbri init` records each stream it creates in `pins`, a text file in the keys directory
(`--keys`, else `$TENBRI_KEYS`, else the default; never inside a stream), one line per stream, like
ssh's `known_hosts`:

```text
/…/tenbri-demo/audit/support sha256:cb2db297f1a4250ac01da3d5eaa8498fa331d9f5217f792468587b8f0972d104
```

The location is the stream directory's absolute path, symlinks resolved (so `audit/support` and `./audit/support`
from the same directory match), or an `s3://` or `r2://` URL as given. When a location appears
more than once, the last line wins: a stream created again at the same place is pinned anew. The
file is only appended to; nothing else writes it.

`verify` and `show` without `--key`, and `query` and `tail` with one-line output, look up the
stream's location in it. `--key` always wins. JSON output of `query` and `tail` never uses it.

A recorded pin is only as good as the machine that holds it: it lets you skip `--key` on the
machine that ran `tenbri init`. Anyone else (an auditor, CI, another laptop) passes `--key` with
the fingerprint `init` printed. Streams created by `init()` in Python or TypeScript, by the Rust
`Writer` or by `tenbrid` are not recorded; pass `--key` for them, or add their line yourself.

If `init` cannot append to the file, it exits 2 with `<keys>/pins: <error>` after the stream is
created; pass `--key` to read it.

<Callout type="warn" title="Planned">
`gc`, `export`, `mcp`, `proxy` and `ingest` are planned and not built.
</Callout>

## Exit codes

Stable from 0.1.0.

| Code | Meaning |
| --- | --- |
| `0` | Success |
| `1` | The stream does not verify, or does not match the `--checkpoint` given (truncated behind it, rewritten, or not signed by the stream); the first broken sequence number is printed. Also: `schema check` found an entry that breaks its action's schema; `receipt verify` found a receipt that does not verify; `query`, `show`, `tail` or `receipt create` read a stream that does not verify; `query` found a batch holding one of its answers edited since it was indexed; `query --verify` found the index disagreeing with the stream. |
| `2` | Any other error, a malformed checkpoint file among them |
| `3` | `verify` without `--key` and without a pin `tenbri init` recorded: the stream is consistent with its own genesis key, which proves nothing about who wrote it. Until 0.1.0-beta.3, `verify` without `--key` always exited 3. |

## Environment variables

| Variable | Used for |
| --- | --- |
| `TENBRI_STREAM` | The stream `PATH` when it is left out, for every command that takes one |
| `TENBRI_KEYS` | Keys directory when `--keys` is not given; its `pins` file holds the recorded pins |
| `XDG_CONFIG_HOME`, `HOME` | Default keys directory (`$XDG_CONFIG_HOME/tenbri/keys`, else `~/.config/tenbri/keys`) |
| `APPDATA` | Default keys directory on Windows |
| `TENBRI_INDEX_DIR` | Where query indexes live |
| `XDG_CACHE_HOME`, `LOCALAPPDATA` | Default index directory (`$XDG_CACHE_HOME/tenbri/index`, else `~/.cache/tenbri/index`; `~/Library/Caches/tenbri/index` on macOS; `%LOCALAPPDATA%\tenbri\index` on Windows) |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION` and the other `AWS_*` | Credentials for `s3://` and `r2://` |
| `AWS_ENDPOINT_URL`, `AWS_ALLOW_HTTP` | S3-compatible endpoint (MinIO); `AWS_ALLOW_HTTP=true` for plain HTTP |
| `CLOUDFLARE_ACCOUNT_ID` | R2 endpoint, when `AWS_ENDPOINT_URL` is not set |

Details per backend are in [Storage](/docs/reference/storage/).
