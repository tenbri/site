An adapter plugs into an agent framework's own hooks and writes what the agent does into a Tenbri
stream. Open a stream with the Python or Node binding, hand it to the adapter, and run your agent as
before. Each tool call becomes a decision: an **intent** that is durable before the tool runs, then
an **outcome** once it has run.

Each adapter is released with the `tenbri` binding, at the same version. While Tenbri is in
pre-release, install with `pip install --pre` and the `@next` npm tag. Each one is tested in CI
with no model and no API key: the Claude adapter drives the real SDK against a stand-in for the
Claude Code CLI, and the OpenAI and LangGraph adapters run their framework with a scripted model.
Each page shows how to do the same in your own tests.

## Why an adapter

You could call `intent` and `outcome` around every tool yourself, and for a framework without an
adapter you should ([here is how](/docs/adapters/planned/#use-tenbri-from-any-framework-today)).
An adapter does it at the one place every tool call passes through, so a new tool is recorded the
day it is added, approvals are tied to the calls they allowed, and nothing in your tools changes.

## What gets recorded

Every adapter follows the same mapping:

| Agent event | Tenbri entry |
| --- | --- |
| A tool call is about to run | An `intent` decision. `principal` is the agent, `action.type` is the tool name (or a name you map it to), `action.target` comes from the tool's arguments when you say how. |
| The tool returned | The `outcome` with status `ok` |
| The tool raised or failed | The `outcome` with status `error` |
| A person or a rule denied the call | The `outcome` with status `refused` |
| The run was interrupted mid-tool, or the process died | `unknown`: from the adapter on interrupt, or from the next writer that reconciles the open intent |
| A person approved the call | An `approval` entry by that person; the decision names it in its `approval` member ([approvals](/docs/concepts/streams-and-entries/#approvals)) |
| A handoff to another agent (OpenAI Agents SDK) | An `intent` and an `ok` outcome, action `handoff`, target `agent:<next agent>` |

How each framework's events map:

| Tenbri entry | Claude Agent SDK | OpenAI Agents SDK | LangGraph and LangChain |
| --- | --- | --- | --- |
| `intent` | `PreToolUse` hook | `on_tool_start` (Python), a `tenbri` tool input guardrail (TypeScript) | `on_tool_start` / `handleToolStart` callback |
| outcome `ok` | `PostToolUse` | the tool returned | `on_tool_end` / `handleToolEnd` |
| outcome `error` | `PostToolUseFailure` | the tool raised or timed out | the tool raised, or returned an error `ToolMessage` |
| outcome `refused` | `can_use_tool` denied, or `PermissionDenied` | a guardrail rejected the call, or `recorder.reject(...)` | the tool raised `tenbri.Refused`, or a person rejected the interrupt (`resume`) |
| outcome `unknown` | `PostToolUseFailure` with an interrupt | the run was cancelled (Python) | a LangGraph interrupt inside the tool |
| `approval` | `can_use_tool` allowed, with an `approver` | `recorder.approve(...)` | a person approved or edited the interrupt (`resume`), or `approve(...)` |

See [Streams and entries](/docs/concepts/streams-and-entries/) for the entry kinds.

## Guarantees

- **Fail closed.** If the intent cannot be written, the tool does not run. Each adapter has a
  fail-open switch (`fail_open` / `failOpen`) that lets the tool run unrecorded, with a warning.
- **No prompts stored.** Adapters never write prompts, tool arguments or tool results. You choose
  what goes into `action.target`.
- **Keyed digests.** When the stream is opened with a digest key, an adapter pins a tool's input,
  or a document the agent read, by its keyed digest (an entry in `inputs`). Whoever holds the
  content and the key can prove what the agent used; nobody can guess it from the log.
- **Trace ids.** Entries carry the active trace id when there is one, so a decision and its trace
  find each other.
