`TenbriHooks` adds Tenbri's hooks next to your own in the
[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk) options, and wraps your
`can_use_tool` (`canUseTool` in TypeScript) callback. Every tool call the agent makes becomes a
decision in a Tenbri stream, with the intent durable before the tool runs.

## Install from source

You need a Rust toolchain (the bindings compile from source), Git, and Python 3.10 or later or
Node 20 or later.

<Tabs syncKey="lang">
<TabItem label="Python">

```sh
git clone https://github.com/tenbri/tenbri
cd tenbri
python -m pip install ./bindings/python ./adapters/claude-agent-sdk/python
```

This installs the `tenbri` binding, `tenbri-claude-agent-sdk`, and `claude-agent-sdk` 0.1.81 or
later. For trace ids on entries, also install `opentelemetry-api`.

</TabItem>
<TabItem label="TypeScript">

Build the Node binding, then build and pack the adapter:

```sh
git clone https://github.com/tenbri/tenbri
cd tenbri/bindings/node
npm ci && npx napi build --platform
cd ../../adapters/claude-agent-sdk/typescript
npm ci && npm run build && npm pack
```

Then, in your project (replace `/path/to/tenbri` with your clone):

```sh
npm install /path/to/tenbri/bindings/node \
  /path/to/tenbri/adapters/claude-agent-sdk/typescript/tenbri-claude-agent-sdk-0.0.0.tgz \
  @anthropic-ai/claude-agent-sdk
```

The binding is installed as a link to your clone, so keep the clone. The adapter needs
`@anthropic-ai/claude-agent-sdk` 0.2.141 or later. For trace ids on entries, also install
`@opentelemetry/api` and a context manager.

</TabItem>
</Tabs>

## A minimal example

A support agent with one tool, `issue_refund`, served from an in-process MCP server. The tool asks
a person first; their answer is recorded as an approval. `describe` turns the tool call into the
decision's action, target and rule. This is the repository's refund example, shortened.

<Tabs syncKey="lang">
<TabItem label="Python">

```python
import asyncio
from claude_agent_sdk import (
    ClaudeAgentOptions, PermissionResultAllow, PermissionResultDeny,
    create_sdk_mcp_server, query, tool,
)
from tenbri import AsyncTenbri
from tenbri_claude_agent_sdk import TenbriHooks


@tool("issue_refund", "Refund a Stripe charge", {"charge": str, "amount_eur": int})
async def issue_refund(args):
    return {"content": [{"type": "text", "text": f"refunded {args['amount_eur']} EUR"}]}


async def ask(tool, tool_input, ctx):
    answer = await asyncio.to_thread(input, f"Allow {tool} {tool_input}? [y/N] ")
    return PermissionResultAllow() if answer.lower() == "y" else PermissionResultDeny(message="no")


def describe(tool, tool_input):
    if tool == "mcp__billing__issue_refund":
        return {
            "action": "issue_refund",
            "target": f"stripe:{tool_input['charge']}",
            "rule": {"ref": "policy:refund", "version": "14", "result": "allow"},
        }
    return None


async def prompt():  # can_use_tool needs a streamed prompt
    content = "Ticket 4512: the customer was charged twice (ch_123, 30 EUR). Refund the duplicate."
    yield {"type": "user", "message": {"role": "user", "content": content}}


async def main():
    log = await AsyncTenbri.open(
        "./audit/support", create=True, digest_key=b"a 32-byte secret, kept apart...."
    )
    hooks = TenbriHooks(log, "agent:support", describe=describe, approver="person:alice")
    options = hooks.instrument(ClaudeAgentOptions(
        mcp_servers={"billing": create_sdk_mcp_server("billing", tools=[issue_refund])},
        tools=[],  # no built-in tools: only the refund, which asks first
        can_use_tool=ask,
    ))
    async for message in query(prompt=prompt(), options=options):
        print(type(message).__name__)

    print("verified:", (await log.verify(log.fingerprint)).ok)
    for m in await log.query(action="issue_refund"):
        e = m.entry
        print(e["seq"], e.get("phase"), e.get("status", ""), e["action"], e.get("approval", ""))
    await log.close()


asyncio.run(main())
```

```ts
import { createInterface } from 'node:readline/promises'
import { createSdkMcpServer, query, tool, type CanUseTool, type SDKUserMessage } from '@anthropic-ai/claude-agent-sdk'
import { Tenbri } from 'tenbri'
import { TenbriHooks } from '@tenbri/claude-agent-sdk'
import { z } from 'zod'

const billing = createSdkMcpServer({
  name: 'billing',
  tools: [
    tool('issue_refund', 'Refund a Stripe charge', { charge: z.string(), amount_eur: z.number().int() }, async (a) => ({
      content: [{ type: 'text', text: `refunded ${a.amount_eur} EUR` }],
    })),
  ],
})

const ask: CanUseTool = async (name, input) => {
  const rl = createInterface({ input: process.stdin, output: process.stdout })
  const answer = await rl.question(`Allow ${name} ${JSON.stringify(input)}? [y/N] `)
  rl.close()
  return answer.toLowerCase() === 'y' ? { behavior: 'allow', updatedInput: input } : { behavior: 'deny', message: 'no' }
}

// canUseTool needs a streamed prompt
async function* prompt(): AsyncGenerator<SDKUserMessage> {
  const content = 'Ticket 4512: the customer was charged twice (ch_123, 30 EUR). Refund the duplicate.'
  yield { type: 'user', message: { role: 'user', content }, parent_tool_use_id: null, session_id: '' }
}

const log = await Tenbri.open('./audit/support', { create: true, digestKey: 'a 32-byte secret, kept apart....' })
const hooks = new TenbriHooks(log, {
  principal: 'agent:support',
  approver: 'person:alice',
  describe: (name, input) =>
    name === 'mcp__billing__issue_refund'
      ? { action: 'issue_refund', target: `stripe:${input.charge}`, rule: { ref: 'policy:refund', version: '14', result: 'allow' } }
      : undefined,
})
const options = hooks.instrument({
  mcpServers: { billing },
  tools: [], // no built-in tools: only the refund, which asks first
  canUseTool: ask,
})
for await (const message of query({ prompt: prompt(), options })) console.log(message.type)

console.log('verified:', (await log.verify(log.fingerprint ?? undefined)).ok)
for (const { entry: e } of await log.query({ action: 'issue_refund' })) {
  console.log(e.seq, e.phase, e.status ?? '', e.action, e.approval ?? '')
}
await log.close()
```

The example uses `zod` for the tool's schema: `npm install zod`.

## Options

`TenbriHooks(log, principal, ...)` in Python, `new TenbriHooks(log, { principal, ... })` in
TypeScript.

| Python | TypeScript | Default | What it does |
| --- | --- | --- | --- |
| `principal` | `principal` | required | The agent, for example `"agent:support"`. |
| `tools` | `tools` | every tool | Names to record, or a predicate of the tool name. |
| `describe` | `describe` | `default_describe` / `defaultDescribe` | `(tool, input)` to the intent's fields: `target`, `inputs` (`{ref, version, digest}`), `rule`, `subject`, or `action` to rename the action. The default records only the target of the file and web tools (`file_path`, `notebook_path`, `path`, `url`). |
| `approver` | `approver` | none | Who approves through `can_use_tool`: a principal such as `"person:alice"`, or a function of the call returning one. Leave it unset when your own code decides and no person approves. |
| `fail_open` | `failOpen` | `False` / `false` | Let a tool run, unrecorded, when its intent could not be written. A warning is logged. |
| `timeout` | `timeout` | `2.0` seconds / `2000` ms | How long the intent may take to become durable before the tool fails closed (or runs, with `fail_open`). |

`instrument(options)` returns your options with Tenbri's hooks added to yours (`PreToolUse`,
`PostToolUse`, `PostToolUseFailure`, `PermissionDenied`) and your `can_use_tool` wrapped. If you
build options another way, `hooks.can_use_tool(fn)` (`hooks.canUseTool(fn)`) wraps a callback on
its own. The module also exports `entry_hash` (`entryHash`), the hash an `approval` member names.

## What is written

| SDK event | Entry |
| --- | --- |
| `PreToolUse` | An `intent`: principal the agent, `action.type` the tool name, `action.target` from `describe`. Durable before the tool runs. |
| `can_use_tool` allows, with an `approver` | An `approval` by that person, for the same action |
| `PostToolUse` | The outcome `ok`, naming the approval if there was one |
| `PostToolUseFailure` | The outcome `error`, or `unknown` when the tool was interrupted |
| `can_use_tool` denies, or `PermissionDenied` | The outcome `refused` |

Nothing of the prompt, the tool input or the tool output is stored. When the stream was opened with
a digest key (`digest_key` / `digestKey`), the intent pins the tool input by its keyed digest, as an
input with `ref` `claude:tool_input` and the tool use id as its `version`. The intent from the run
above, as stored (signatures and hashes shortened):

## Approvals and permission prompts

The SDK calls `can_use_tool` when a tool needs permission. The adapter wraps your callback and acts
on its answer:

- **Allowed, with an `approver`:** an `approval` entry by that principal is written, for the same
  action as the intent. The tool's outcome names it in `approval`. If the approval cannot be
  written, the tool is denied (unless `fail_open`).
- **Allowed, no `approver`:** nothing extra. Your code decided, not a person.
- **Denied:** the intent's outcome is `refused`. A denial outside `can_use_tool` (a permission rule,
  auto mode) reaches the `PermissionDenied` hook and is also `refused`.

Tools that never ask (allowed by your settings) get an intent and an outcome, with no approval.
`can_use_tool` itself needs a streamed prompt (an async iterable), as the SDK requires.

## Limits

- **Fail closed by default.** A tool whose intent is not durable within `timeout` is denied, and
  the agent sees why. Set `fail_open` only if running unrecorded is acceptable.
- **A crash leaves an open intent.** If the process dies after `PreToolUse`, no outcome is written;
  the next writer of the stream reconciles that intent as `unknown`.
- **An outcome that cannot be written is logged, not retried.** The tool already ran, so the open
  intent is reconciled as `unknown` later.
- **Only targets of file and web tools by default.** For commands, MCP tools and your own tools,
  write a `describe` to record a target, a rule or a subject.

The stream's signing keys live in `$TENBRI_KEYS`, else `~/.config/tenbri/keys`, unless you pass
`keys` to `open`. See [keys](/docs/concepts/keys/).
