A support agent wants to refund a charge. A person, Alice, approves it first. You will record three
entries with the `tenbri` CLI: Alice's `approval`, the agent's `intent` that names that approval by
its entry hash, and the `outcome` with `status: ok`. Then you read them back with `tail` and
`query`, and verify the stream.

**Prerequisites:** the `tenbri` CLI ([install](/docs/getting-started/install/)), `jq`, and
`shasum` (or `sha256sum`).

## 1. Create the stream

Keys live in `$TENBRI_KEYS` (default `~/.config/tenbri/keys`), never inside the stream. This
recipe keeps them next to it, in `./keys`.

```sh
export TENBRI_KEYS=./keys
tenbri init audit/support
```

```text
created stream tnb1:df45634fd5c68a9fc1062f17755cad7f at audit/support
stream key fingerprint (pin it): sha256:df45634fd5c68a9fc1062f17755cad7f5d1d1ff3a86b0fbafc69bf1f744a8406
keys: ./keys/tnb1-df45634fd5c68a9fc1062f17755cad7f
verify with: tenbri verify audit/support --key sha256:df45634fd5c68a9fc1062f17755cad7f5d1d1ff3a86b0fbafc69bf1f744a8406
```

`init` writes two key entries (seq 1 and 2): the stream key and the first session key.

## 2. Record the approval

An `approval` entry needs a `principal` (the approver) and an `action` (what is approved).
`tenbri append` reads the draft on stdin and prints the entry as stored.

```sh
APPROVAL=$(tenbri append audit/support <<'EOF'
{
  "kind": "approval",
  "principal": {"kind": "person", "id": "alice"},
  "action": {"type": "issue_refund", "target": "stripe:charge/ch_3PqX"}
}
EOF
)
echo "$APPROVAL"
```

```text
{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"id":"01M5CT6J7RFD5TKGBQN04AK0TD","kind":"approval","prev":"sha256:33268eea…","principal":{"id":"alice","kind":"person"},"seq":3,"sig":"ed25519:bead7761…","signer":"sess:2026-10-20:55bd420d39d5","stream":"tnb1:df45634fd5c68a9fc1062f17755cad7f","ts":"2026-10-20T14:07:15.704Z","v":1}
```

## 3. Compute the approval's entry hash

An intent cites an approval as `{"by": <approver>, "entry": <entry hash>}`. The entry hash is
SHA-256 of a zero byte followed by the stored line, as `sha256:<hex>`.

```sh
APPROVAL_HASH="sha256:$(printf '\0%s' "$APPROVAL" | shasum -a 256 | cut -d' ' -f1)"
echo "$APPROVAL_HASH"
```

```text
sha256:e2f1940e5a4fad38be3a14d56580327466c33799e14db1ef64961b3077c2fd00
```

## 4. Record the intent

The intent is written, and durable, before the refund runs. It carries the policy it read, the rule
that allowed it, and the approval.

```sh
INTENT=$(tenbri append audit/support <<EOF
{
  "kind": "decision",
  "phase": "intent",
  "source": "sdk",
  "principal": {"kind": "agent", "id": "support-assistant"},
  "action": {"type": "issue_refund", "target": "stripe:charge/ch_3PqX"},
  "inputs": [{"ref": "policy:refund", "version": "14", "digest": "hmac-sha256:9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa"}],
  "rule": {"ref": "rule:refund-under-100", "version": "3", "result": "allow"},
  "approval": {"by": {"kind": "person", "id": "alice"}, "entry": "$APPROVAL_HASH"}
}
EOF
)
echo "$INTENT"
```

```text
{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"approval":{"by":{"id":"alice","kind":"person"},"entry":"sha256:e2f1940e5a4fad38be3a14d56580327466c33799e14db1ef64961b3077c2fd00"},"id":"01M5CT6JA9PHWK2Y0BSFBN98M2","inputs":[{"digest":"hmac-sha256:9f2c41aa…","ref":"policy:refund","version":"14"}],"kind":"decision","phase":"intent","prev":"sha256:e2f1940e5a4fad38be3a14d56580327466c33799e14db1ef64961b3077c2fd00","principal":{"id":"support-assistant","kind":"agent"},"rule":{"ref":"rule:refund-under-100","result":"allow","version":"3"},"seq":4,"sig":"ed25519:504a0994…","signer":"sess:2026-10-20:55bd420d39d5","source":"sdk","stream":"tnb1:df45634fd5c68a9fc1062f17755cad7f","ts":"2026-10-20T14:07:15.785Z","v":1}
```

The intent's `prev` equals `APPROVAL_HASH`: the approval is the entry just before it, so the hash
you computed is the one the chain uses. An `approval.entry` that does not name an earlier approval
entry is refused with `bad_approval`.

## 5. Record the outcome

After the refund call returns, close the intent by its `id`.

```sh
INTENT_ID=$(echo "$INTENT" | jq -r .id)
tenbri append audit/support <<EOF
{
  "kind": "decision",
  "phase": "outcome",
  "source": "sdk",
  "intent": "$INTENT_ID",
  "status": "ok",
  "principal": {"kind": "agent", "id": "support-assistant"},
  "action": {"type": "issue_refund", "target": "stripe:charge/ch_3PqX"}
}
EOF
```

```text
{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"id":"01M5CT6JB9SG7TH3PEJF1SSQ1Z","intent":"01M5CT6JA9PHWK2Y0BSFBN98M2","kind":"decision","phase":"outcome","prev":"sha256:bac1cfa2…","principal":{"id":"support-assistant","kind":"agent"},"seq":5,"sig":"ed25519:6707bcb8…","signer":"sess:2026-10-20:55bd420d39d5","source":"sdk","status":"ok","stream":"tnb1:df45634fd5c68a9fc1062f17755cad7f","ts":"2026-10-20T14:07:15.817Z","v":1}
```

## 6. Read the entries back

`tail` prints the last entries as stored. `--no-follow` exits instead of waiting for new ones.

```sh
tenbri tail audit/support -n 3 --no-follow
```

```text
{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"id":"01M5CT6J7RFD5TKGBQN04AK0TD","kind":"approval",…,"seq":3,…}
{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"approval":{"by":{"id":"alice","kind":"person"},"entry":"sha256:e2f1940e…"},"id":"01M5CT6JA9PHWK2Y0BSFBN98M2",…,"phase":"intent",…,"seq":4,…}
{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"id":"01M5CT6JB9SG7TH3PEJF1SSQ1Z","intent":"01M5CT6JA9PHWK2Y0BSFBN98M2",…,"phase":"outcome",…,"seq":5,…,"status":"ok",…}
```

`query` filters by action or input and wraps each entry with its verification status. With
`--key`, the stream is checked against the pinned fingerprint first.

```sh
tenbri query audit/support --action issue_refund \
  --key sha256:df45634fd5c68a9fc1062f17755cad7f5d1d1ff3a86b0fbafc69bf1f744a8406 \
  | jq -c '{verification, seq: .entry.seq, kind: .entry.kind, phase: .entry.phase, status: .entry.status, approval: .entry.approval.by.id}'
```

```text
{"verification":"verified","seq":3,"kind":"approval","phase":null,"status":null,"approval":null}
{"verification":"verified","seq":4,"kind":"decision","phase":"intent","status":null,"approval":"alice"}
{"verification":"verified","seq":5,"kind":"decision","phase":"outcome","status":"ok","approval":null}
```

## 7. Verify

```sh
tenbri verify audit/support --key sha256:df45634fd5c68a9fc1062f17755cad7f5d1d1ff3a86b0fbafc69bf1f744a8406
```

```text
verified 5 entries, stream tnb1:df45634fd5c68a9fc1062f17755cad7f, pinned to sha256:df45634fd5c68a9fc1062f17755cad7f5d1d1ff3a86b0fbafc69bf1f744a8406
```

## What happened

You wrote three signed entries that chain to each other. The intent cites the approval by its
entry hash, so the approval cannot be swapped or edited without breaking verification. The outcome
names its intent by `id`, which closes it: an intent without an outcome is reconciled with
`status: unknown` by a later writer after an hour.
