`tenbrid` serves streams over REST and gRPC, so agents in any language can write to them. You will
start it on your machine with one stream and one bearer token, record an intent and its outcome
with `curl`, retry a write safely with the same `Idempotency-Key`, list and tail entries, and ask
the server to verify the stream.

**Prerequisites:** the `tenbri` and `tenbrid` binaries ([install](/docs/getting-started/install/))
and `curl`.

## 1. Create the stream and a token

```sh
export TENBRI_KEYS=./keys
tenbri init audit/support
tenbrid token
```

```text
created stream tnb1:bb63fd4f0deb4a5220d91220c3088e00 at audit/support
stream key fingerprint (pin it): sha256:bb63fd4f0deb4a5220d91220c3088e003d3810d16e4d8adf2c0eff92be8ee4e5
keys: ./keys/tnb1-bb63fd4f0deb4a5220d91220c3088e00
verify with: tenbri verify audit/support --key sha256:bb63fd4f0deb4a5220d91220c3088e003d3810d16e4d8adf2c0eff92be8ee4e5
token (give it to the client; it is not stored): tnbt_0b7ad927…

[[tokens]]
sha256 = "sha256:458793b41a8061f347816d886e6d55022e39cc11c8c0045b4bfbfa9ac17c2e12"
principal = { kind = "agent", id = "..." }
```

Keep the token for the client: `tenbrid` stores only its hash.

## 2. Configure and start tenbrid

Each token is bound to one principal; entries written with it carry that principal.

```toml title="tenbrid.toml"
[streams.support]
path = "audit/support"

[[tokens]]
sha256 = "sha256:458793b41a8061f347816d886e6d55022e39cc11c8c0045b4bfbfa9ac17c2e12"
principal = { kind = "agent", id = "support-assistant" }
```

REST listens on `127.0.0.1:7070` and gRPC on `127.0.0.1:7071` by default. `TENBRI_LISTEN` and
`TENBRI_GRPC_LISTEN` (or `listen` and `grpc_listen` in the file) change them. `TENBRI_KEYS` is
read from the environment, as `tenbri` does.

```sh
TENBRI_LISTEN=127.0.0.1:8080 TENBRI_GRPC_LISTEN=127.0.0.1:8081 tenbrid --config tenbrid.toml
```

```text
tenbrid 0.1.0-alpha.2: REST on http://127.0.0.1:8080, gRPC on 127.0.0.1:8081, 1 streams
```

In another terminal:

```sh
export TOKEN=tnbt_0b7ad927…   # the token printed in step 1
curl -s http://127.0.0.1:8080/v1/health
curl -s http://127.0.0.1:8080/v1/streams/support/entries
```

```text
{"status":"ok"}
{"error":{"code":"TENBRI_UNAUTHENTICATED","message":"send Authorization: Bearer <token>"}}
```

Only `/v1/health` and `/v1/ready` answer without a token.

## 3. Write an intent

Every write carries an `Idempotency-Key`: the entry id, a ULID your client generates. `kind` and
`phase` come from the route, `principal` from the token, `source` defaults to `sdk` and
`durability` to `local`.

```sh
curl -s -X POST http://127.0.0.1:8080/v1/streams/support/intents \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: 01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A" \
  -H "Content-Type: application/json" \
  -d '{"action":{"type":"issue_refund","target":"stripe:charge/ch_3PqX"},"inputs":[{"ref":"policy:refund","version":"14","digest":"hmac-sha256:9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa"}]}'
```

```text
{"entry":{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"durability":"local","id":"01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A","inputs":[{"digest":"hmac-sha256:9f2c41aa…","ref":"policy:refund","version":"14"}],"kind":"decision","phase":"intent","prev":"sha256:557159f2…","principal":{"id":"support-assistant","kind":"agent"},"seq":3,"sig":"ed25519:7b39a352…","signer":"sess:2026-10-20:b7d7adc39198","source":"sdk","stream":"tnb1:bb63fd4f0deb4a5220d91220c3088e00","ts":"2026-10-20T14:08:57.436Z","v":1},"replayed":false}
```

The response comes back once the intent is durable, so the action can run. Send the same request
again (a retry after a timeout, say) and you get the original entry back, with status 200 and
`"replayed":true`, instead of a second entry:

```sh
curl -s -w '\n%{http_code}\n' -X POST http://127.0.0.1:8080/v1/streams/support/intents \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: 01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A" \
  -H "Content-Type: application/json" \
  -d '{"action":{"type":"issue_refund","target":"stripe:charge/ch_3PqX"},"inputs":[{"ref":"policy:refund","version":"14","digest":"hmac-sha256:9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa9f2c41aa"}]}'
```

```text
{"entry":{…,"id":"01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A",…,"seq":3,…},"replayed":true}
200
```

A first write answers 201. Reusing the key for a different draft is refused with 409:

```text
{"error":{"code":"TENBRI_IDEMPOTENCY_CONFLICT","message":"id 01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A was used for a different entry"}}
409
```

## 4. Write the outcome

An outcome needs only `intent` and `status`; `principal`, `action`, `subject` and `source` default
to the intent's.

```sh
curl -s -X POST http://127.0.0.1:8080/v1/streams/support/outcomes \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: 01K7ZJ4R8N2B6C4D9E1F3G5H7J" \
  -H "Content-Type: application/json" \
  -d '{"intent":"01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A","status":"ok"}'
```

```text
{"entry":{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"id":"01K7ZJ4R8N2B6C4D9E1F3G5H7J","intent":"01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A","kind":"decision","phase":"outcome","prev":"sha256:648d0fc5…","principal":{"id":"support-assistant","kind":"agent"},"seq":4,"sig":"ed25519:93296239…","signer":"sess:2026-10-20:b7d7adc39198","source":"sdk","status":"ok","stream":"tnb1:bb63fd4f0deb4a5220d91220c3088e00","ts":"2026-10-20T14:08:57.497Z","v":1},"replayed":false}
```

## 5. List entries

`GET /v1/streams/{stream}/entries` filters by `input`, `action`, `principal`, `target`, `subject`
and `after_seq`, with `limit` (default 100, at most 1000).

```sh
curl -s "http://127.0.0.1:8080/v1/streams/support/entries?input=policy:refund@14" \
  -H "Authorization: Bearer $TOKEN"
```

```text
{"entries":[{"verification":"verified","entry":{"action":{"target":"stripe:charge/ch_3PqX","type":"issue_refund"},"durability":"local","id":"01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A","inputs":[{"digest":"hmac-sha256:9f2c41aa…","ref":"policy:refund","version":"14"}],"kind":"decision","phase":"intent",…,"seq":3,…}}]}
```

`?action=issue_refund` returns both the intent and the outcome.

## 6. Tail

`/tail` is a server-sent event stream: the entries after `after_seq`, then new ones as they are
written. Each event's `id` is the entry's sequence number, so a client reconnects with
`Last-Event-ID`.

```sh
curl -s -N "http://127.0.0.1:8080/v1/streams/support/tail?after_seq=2" \
  -H "Authorization: Bearer $TOKEN"
```

```text
event: entry
id: 3
data: {"verification":"verified","entry":{…,"id":"01K7ZJ4Q3V8M2R6T9W1X5Y7Z0A",…,"phase":"intent",…,"seq":3,…}}

event: entry
id: 4
data: {"verification":"verified","entry":{…,"id":"01K7ZJ4R8N2B6C4D9E1F3G5H7J",…,"phase":"outcome",…,"seq":4,…,"status":"ok",…}}
```

## 7. Verify

The server reads the whole stream from storage and checks it against its pinned key. `broken` is
absent when the stream verifies.

```sh
curl -s http://127.0.0.1:8080/v1/streams/support/verify \
  -H "Authorization: Bearer $TOKEN"
```

```text
{"stream":"tnb1:bb63fd4f0deb4a5220d91220c3088e00","entries":4,"pinned_key":"sha256:bb63fd4f0deb4a5220d91220c3088e003d3810d16e4d8adf2c0eff92be8ee4e5"}
```

Stop `tenbrid` with Ctrl+C. It finishes the writes in flight first:

```text
tenbrid: stopped; every acknowledged entry is durable
```

## What happened

`tenbrid` signed and chained each entry exactly as `tenbri append` does, using the stream's session
key from `TENBRI_KEYS`, and stamped the token's principal on it. The `Idempotency-Key` became the
entry id, which makes retries safe. The stream on disk is a normal stream: `tenbri verify
audit/support --key …` checks it without the server.
